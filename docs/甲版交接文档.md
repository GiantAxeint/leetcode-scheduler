## 2. 三个转折点

### 第一次：从「卡驱动」到「题驱动」

这是整个项目性质变化的一次，发生在 10-30 18:32。

原来的设计是：题型卡有五档间隔，卡到日子就复习整张卡，卡上挂的题跟着一起过。

你当时说的是：

> 我再说一遍，题型卡是用来归纳复习的，不应该是调度单位。

这句话推翻了我前几轮一直在维护的地基。我给了甲（只给未归题的题加状态）和乙（全部改题目级）两个方案，你选了乙。

改完之后：`problem` 表自己带 `stage` / `next_due`，`card_state` 变成死表（至今没删），`state.py` 整个废掉。

**这件事值得记住的地方**：我当时判断"乙改动太大，先做甲"。这个判断是错的——如果先做了甲，系统里会长期存在两套间隔，而你迟早会要求合并。绕路不如一次到位。

### 第二次：答错的处理方式

10-30 18:53。你提的规则是「1 天后错了 → 之后改成 2,6,14,29」，并且自己说"我感觉有问题"。

你的直觉是对的：2,6,14,29 大约是 1,3,7,15 的两倍，那等于**错得越多的题，复习得越少**。

我查了 Anki 和墨墨的实际做法（Anki 官方 FAQ、墨墨的算法更新日志），两家都是"错 → 间隔缩短"。最后选了 Anki 式的「退一档 + 打五折」，你拍了板。

**这次的价值不在于算法，在于你怀疑自己的规则并让我去查证。** 如果我顺着你的数字实现，这个系统会安静地反向工作很久。

### 第三次：「已成」这个出口

11-02 10:42。你要把「积压」改成「已成」，右键可以把题扔进任意队列。

这不是功能追加，这是给系统加了一个**人工出口**。在此之前，题只有一条路出池：走完 5 档。而现实是——有些题你做三次就会了，硬走 30 天纯属浪费名额。

加了之后，整个循环才闭合：自动出池管"按节奏记住的"，手动标成管"已经会了的"。

## 3. 规则快照（截至甲版结束）

```
档位      S0 新题 → S1(1天) → S2(3天) → S3(7天) → S4(15天) → S5(30天) → 出池
答对      0 → 2（首答跳过 1 天档），其余升一档；S5 再答对 → 已成
答错      退一档，下次间隔 = 该档基数 × 0.5，最小 1 天

队列      候补 → 在途（名额 36）→ 已成
补位      出池 / 删除 / 手动移出 → 候补队头补一个
回收      逾期超过 7 天 → 自动退回候补，档位保留

日历      只排周一到周五；到期日落在周末 → 顺延到下一个工作日
          周末录的题，第一次复习从周一开始
          周末仍可手动加题、拖拽、判定、记录

判定      二元：答对 / 未答对。一天只判一次（后来的窗口加的锁）
```

在途名额从 15 改到 36，是在 11-02 那次对话里算出来的：每天 3 道新题，名额 36 时每天到期约 3.7 道，整体控制在 1.5 小时。这个数字不是我拍的，是拿吞吐量倒推的，改之前建议先重算一遍。

## 4. 踩出来的坑

| 坑 | 后果 | 教训 |
|---|---|---|
| 在 `schema.sql` 里给新列建索引 | 老库启动直接 500，所有接口全挂 | 依赖新列的索引必须放在 `migrate()` 之后建。`init()` 的顺序是：建表 → 迁移 → 建索引 |
| `SELECT * FROM problem` 却在前端用 `p.cards` | 已成清单全部归到「未归题型」 | 接口返回的字段和前端消费的字段要对得上；今日任务的 SQL 有 cards，题目列表没有，就这么错了两天 |
| `/api/today` 只按日期过滤，不看 phase | 标成已成的题还在今日任务里显示 | 只要题有状态，查询就必须过滤状态 |
| `cp -rf` 覆盖运行中的 exe | exe 更新了但进程还跑旧代码 | 部署完必须重启；托盘退出再打开 |
| git push 依赖 VPN | 反复失败，最长卡了两天 | 仓库已设 `http.proxy ""`，直连；VPN 断了就用 `tools/gh_upload.py` 走 API |
| 判断"改动太大先做小的" | 走了弯路 | 见转折点一 |

## 5. 我判断错的地方

写下来，免得后面的人把我当权威。

**1. 「先甲后乙」的保守建议错了。**
当时我建议先做轻量方案，理由是风险小。实际上双轨制的混乱成本远大于一次重构。该一次做完的时候，别分批。

**2. 算"刷完 1500 题要多久"时，我答的是数学题，不是你的问题。**
我算出 15.8 年，还给了张提速表。你的回答是"我每天本来就打算干五个题，调度是用来复习的"。你说得对——我从头到尾把"刷完"当成了目标，而你要的是"记住"。**问题定义错了，算得再准也没用。**

**3. 一开始把「积压」直接删掉，没给替代。**
11-02 改成「已成」时，我把积压提示一并去掉了，之后才想起来补一句"要的话我加个提示"。删东西之前该先想清楚它承担的信息去哪。

## 7. 想说的话

这个窗口从 10 月 30 日下午开到现在，一共八天。

前面大半时间在改功能，后面几天你开始问"这样够不够""要多久""选哪个"。后半段其实比前半段重要——前七天我们在修工具，最后两天在讨论要不要用这个工具。

**关于那个 15.8 年。**
那个数字是吓人的，但它吓人的方式不对。它不是在说"你来不及"，它是在说"你把这套系统当成了刷题机器，而它其实是记忆机器"。这两件事的节奏差一个数量级。你后来自己说清了：每天五个题照做，调度只管复习。这个分工才对。

**关于蓝桥杯。**
我在 11-02 给过一份时间表，核心那句再说一遍：**省一和国奖的差距不在题量，在稳定性**。省赛四小时十道题，能一遍 AC 六道基本就稳了。刷三百题但每题都要调半天，不如刷两百题每题一次过。

你在系统里点的那个「答对」，最好按"一次提交过"的标准点，不是"最后做出来了"。这个按钮是全系统唯一一个靠自觉的地方，也是唯一一个能骗人的地方。

**关于工具。**
这东西现在有五个页面、三态队列、档位推进、右键菜单、托盘常驻。它已经比很多人用的笔记软件复杂了。

复杂不是问题，复杂的代价是**调参的时间会挤掉做题的时间**。这个窗口里我们花了大量时间在"在途应该多少""间隔打几折""日历按年还是滚动"这类问题上——这些问题有正确答案，但它们的正确答案不值得花这么久。

如果哪天你发现自己又在调参数而不是在做题，关掉它，去 LeetCode。

**关于这个窗口。**
上下文确实太长了。长到后面每次回答之前，我都要在几十轮对话里找线索，越到后面越容易记串——比如题型卡到底是调度单位还是归纳容器，我在不同轮次里说过两种话。这不是积分的问题，是可靠性在下降。换掉是对的。

这个窗口不归档，我理解为"留着当记录，但不再往里加东西"。那就这样。
