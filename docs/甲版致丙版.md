## 0. 先说清楚这份文档是什么

`docs/甲版交接文档.md` 是**封存记录**——里面记了 19 个提交、三个转折点、"我判断错的地方"，还有一封信。那份是留作纪念的，不是给你用的。

这份是给你用的。

它不重复三件事：路径（乙版写了）、部署坑（乙版写了 8 个）、代码结构（你看代码比我快）。它只写**代码里读不出来的东西**：用户怎么说话、哪些规矩是他定的、我说过哪些话要打折听。

三条使用规则：

1. **和《甲版交接文档》冲突时，以这份为准。** 我已经把自己已知的错处列在 §3。
2. **从这份开始，别再新增交接文档。** 你接手时 `docs/` 下已经有七份（SPEC、交接说明、进度快照、甲版、乙版、丙版、难度颜色那份），你不得不在 §1.2 建一张对照表才能确定哪个是真的——这就是文档太多的代价。以后直接改这份，加一节"丙版补充"，别开新文件。

3. **甲版在代码里也留了话。** 那些话不好放进文档（要贴着具体行才讲得清），所以写成了注释，标记是 `甲版批注`：

   ```bash
   grep -rn "甲版批注" app/
   ```

   集中在 `scheduler.py`（调度规则为什么这么定）、`db.py`（建库顺序那个 500）、`schema.sql`（`card_state` 不是死表）、`state.py`（死模块）。**读到某段代码觉得"这里写得怪"，先 grep 一下，可能我已经解释过为什么怪。**

## 1. 你上一任为什么吃亏

你说过一句很准的话：**乙版窗口没拿到交接文档，所以犯了不少错。**

但把错处摊开看，她错的不是路径、不是命令、不是架构——那些她自己摸出来了。她错的是"不知道该验什么"：改完前端不打包、打包漏 `--noconsole`、以为源码改了机器上就是新的。三次返工，全是**验证环节**的问题，不是理解环节的问题。

所以这份文档的重心不在"系统长什么样"，在"这个用户怎么验收"。技术债可以读代码还，协作债只能靠传话。

## 2. 用户的行为模式（这一节最值钱）

他用短句下指令，信息密度极高，但**字面之下还有一层**。下面是我在这个窗口里反复撞出来的对照表：

| 他说的话 | 真实含义 | 你该做什么 |
|---|---|---|
| 「你先看我的需求，再给出建议，然后再根据我的反馈更新」 | 别直接改代码 | 先复述需求 → 给方案（最好两个）→ 等他拍板。他明确要求过这个流程 |
| 「我再说一遍，……」 | **你越界了**，不是他没说清 | 停手。把约束原话复述一遍，确认理解，再问要不要回滚 |
| 只丢一张截图，一个字不写 | 他在等你自己反推 | 先描述你看到的现象（"某卡片上是未分类"），再定位。别猜着改 |
| 「我感觉有问题，你查一下 XX」 | 他要查证，不要顺从 | 去查真实产品怎么做，拿证据回来。他推翻过自己的方案 |
| 提一条新规则（如「错一次后改成 2,6,14,29」） | 这是个假设，不是命令 | 先算极端情况：这条规则跑到第 50 次复习会怎样 |
| 「这点小趣味还是保留吧」 | 情绪需求也是需求 | 别把它当噪声优化掉。拖拽排班、壁纸、动效都是这一类 |
| 「要多久 / 改了多少版 / 在途该几个」 | 他在测量，不在寒暄 | 给数，给推导，别给"差不多了" |
| 「结果不好也没关系，你先做」 | 他已经算过风险 | 别再劝，直接干，但要把失败路径想好 |

反面例子，都是我真踩的：

- 他问"刷完 1500 题要多久"，我做了除法答 15.8 年。他回："刷题调度本来就是用来复习的，我每天本来就打算干五个题。" **我算得对，问题问错了。** 他问数字时，先确认他想拿这个数字干什么。
- 我建议"改动太大，先做轻量版（甲），以后再上完整版（乙）"。他直接选乙。**该一次做完的时候分两批，是给未来埋双轨制。**

## 4. 他定的规矩（不是我选的，别改）

这四条是用户原话定的，改之前必须先问：

**4.1 题型卡不是调度单位。**
原话：「我再说一遍，题型卡是用来归纳复习的，不应该是调度单位。」
调度单位是**题**（`problem.phase` / `stage` / `next_due`），题型卡只是容器。任何想把卡重新拉回调度链路的改动，方向就是错的。

**4.2 「已成」是人工出口，不能被自动逻辑覆盖。**
题扔进已成后，不再出现在今日任务、不再参与复习、只能在已成里翻出来。这是他自己给自己上的锁——系统里所有数字都怂恿他多点"答对"，他偏要造一个出口让彻底会的题离桌。**别做"智能判断这题该不该进已成"之类的功能。**

**4.3 判定是二元的，而且靠自觉。**
答对 / 未答对，没有第三态。「答对」的标准是**一次提交过**，不是"最后做出来了"。这个按钮是全系统唯一能骗人的地方，也是唯一不能自动化的地方。

**4.4 参数要留手动改的余地。**
`queue_limit` 默认值不改死成 36——他要在界面上自己调。别替他做决定，哪怕你觉得那个数字更合理。

补充两条他明确说过"不做"的（丙版文档 §2.2 已登记，这里背书）：晚班差异化（只要情绪价值）、清理历史 `build_*/dist_*` 目录（留个纪念）。

## 5. 现在的规则（会腐，用前复核）

基线 `36331f0`，`scheduler.py` 为准：

```
档位     S0 新题 → S1(1d) → S2(3d) → S3(7d) → S4(15d) → S5(30d) → 出池
答对     0 → 2（首答跳过 1 天档）；其余升一档；S5 再答对出池（next_due=None）
答错     退一档，间隔 = 该档基数 × lapse_factor(0.5)，最小 1 天
抖动     interval_fuzz=0.2，作用在最终天数上，1 天档豁免（乙版加）
提前复习 答对：升档，日期取 max(新档推算, 原到期日)
         答错：档位日期都不动 —— 多练一次不该被惩罚（用户明确要的）
容量     daily_capacity=6，早/午/晚只切总量；morning_new=2 固定进早班
周末     skip_weekend=1 时只排工作日，到期落周末顺延；=0 则七天都排
回收     next_due 早于今天-7 天 → 退回 queued，档位保留
避让     next_due 落点超容量 → 找下一个未满工作日；扫 30 天找不到就原样放（丙版加）
```

三条容易误判成 bug 的设计：

1. **今日计划是快照。** `build_plan` 当天生成一次就 return，中途新到期的题不会补进来。这不是漏写。
2. **逾期回收不清档位。** 退候补只改 `phase`，`stage` 留着——他回头还能接着复习。
3. **避让超 30 天就放弃。** 宁可那天超量也不把题推到一个月后，推走等于这道题放假。

这个项目的复杂度已经超过它的使用频率了：六个 tab、拖拽、壁纸、日历、分散、避让。每加一个功能，维护成本上升，而"每天做五道题"这件事一点没变简单。
